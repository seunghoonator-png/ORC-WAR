# ORC-WAR 구현 계획서

> 버전 0.1 · 2026-08-27 · 기준 문서: [DESIGN.md](DESIGN.md)

기획안(DESIGN.md)의 M1~M6 로드맵을 실제 코드 단위로 구체화한 문서.
각 마일스톤은 PR 크기의 작업(Task)으로 쪼개져 있고, 작업마다 완료 기준(DoD)이 있다.

---

## 0. 기술 스택 확정

| 항목 | 선택 | 이유 |
|---|---|---|
| 언어 | **Rust (stable, 2021 edition)** | 단일 정적 exe, 수동 메모리 레이아웃(SoA), fearless concurrency |
| 창/입력/오디오 | **macroquad** | 창 생성·입력·2D 유틸리티가 한 크레이트, 의존성 최소 |
| 유닛 렌더링 | **miniquad 커스텀 파이프라인** (macroquad 하부 레이어) | macroquad 기본 스프라이트 배칭은 CPU 정점 채움 방식이라 30만 유닛 × 60fps에 부족. 인스턴스 버퍼 + 셰이더 확장으로 직접 그린다 |
| 병렬화 | **rayon** | 시뮬 페이즈 내 데이터 병렬 |
| 설정 UI | **egui** (egui-miniquad) | 설정 화면·HUD를 즉시 모드로 빠르게 |
| 직렬화 | **serde + ron** | 전투 설정 파일 저장/공유 |
| 난수 | **자체 xorshift64\*** (시드 고정) | 결정론 보장, 외부 크레이트 불필요 |

의존 크레이트는 위 5개(macroquad, miniquad, rayon, egui 계열, serde/ron)로 제한한다. ECS 프레임워크(bevy, hecs 등)는 **쓰지 않는다** — 30만 유닛에서는 손으로 짠 SoA가 더 빠르고 예측 가능하다.

### 시뮬레이션 상수

```
SIM_HZ            = 20        (dt = 0.05s 고정 스텝)
TICK_BUDGET       = 50 ms     (시뮬 1틱 벽시계 예산, 8코어 기준)
MAX_UNITS         = 300_000
MAX_PROJECTILES   = 200_000   (고정 풀)
WORLD_SIZE        = 3072 × 3072 m
GRID_CELL         = 4 m       (768 × 768 셀)
FLOW_CELL         = 12 m      (256 × 256 셀)
```

단위계: 1.0 = 1m. 위치·속도는 f32(동일 바이너리 내 결정론 충분). 정수 틱 카운터 기반 쿨다운.

## 2. 핵심 자료구조

### 2.1 UnitPool (SoA)

```rust
pub struct UnitPool {
    // hot: 매 틱 전 유닛 순회
    pub pos:      Vec<[f32; 2]>,   // 현재 위치
    pub prev_pos: Vec<[f32; 2]>,   // 렌더 보간용 (직전 틱)
    pub vel:      Vec<[f32; 2]>,
    pub hp:       Vec<f32>,
    pub state:    Vec<UnitState>,  // u8: Advance/Fight/Charge/Brace/Rout/OnWall/Climb/Dead
    pub type_id:  Vec<u8>,         // 병종 인덱스 → UNIT_STATS 테이블
    pub team:     Vec<u8>,         // 0=공격, 1=방어
    // warm
    pub facing:   Vec<f32>,
    pub cooldown: Vec<u16>,        // 남은 틱
    pub target:   Vec<u32>,        // 유닛 idx 또는 NONE
    pub goal:     Vec<u16>,        // 플로우 필드 id
    pub morale:   Vec<u8>,         // 0~200 (0.5 단위)
    pub charge_t: Vec<u16>,        // 돌격 가속 누적 틱
    pub layer:    Vec<u8>,         // 0=지상, 1=성벽 위
}
```

- 총 ≈ **17.4 MB @ 30만** — L3에 hot 배열이 대부분 상주.
- 죽은 유닛은 삭제하지 않고 `Dead` 마킹 + 프리리스트. 틱 말미에 그리드에서만 제외.
- 병종 스탯은 `const UNIT_STATS: [UnitStats; 8]` 정적 테이블. 유닛은 type_id로만 참조.

### 2.2 공간 그리드 (매 틱 재구축)

counting-sort 3패스: ① 셀별 카운트 → ② prefix sum → ③ scatter로 `unit_indices` 연속 배열 완성. 재구축 전체가 O(n)이고 rayon 청크 병렬. 이웃 질의는 3×3 셀 슬라이스 순회.
목표 비용: **재구축 ≤ 3ms, 30만 기준.**

### 2.3 플로우 필드

- 목표(적 본대 중심, 성문, 성벽 구간, 패주 출구 등)당 1장. 동시 활성 ≤ 16장.
- BFS/Dijkstra 적분장(u16 비용) → 8방향 방향장(u8)으로 압축. 1장 = 256×256×3B ≈ 200KB.
- 갱신은 **틱당 1장씩 라운드로빈** (전 필드 0.8s 주기로 순환) — 전선 이동 속도 대비 충분.
- 지형 비용: 평지 1, 숲 3, 여울 4, 오르막 2, 통행불가 ∞.

### 2.4 틱 파이프라인 (World::step)

```
1. ai        : 사이드 목표 재평가(20틱마다) → 유닛 goal/state 갱신 (병렬)
2. flow      : 라운드로빈 1장 재계산 (전용 스레드에 오프로드 가능)
3. movement  : 방향장 추종 + 이웃 분리 + 지형/충돌 → vel, pos 갱신 (병렬, prev_pos 스왑)
4. grid      : 공간 그리드 재구축 (병렬 counting sort)
5. charge    : 돌격 가속/충돌 판정, 브레이스 감지 (병렬)
6. combat    : 근접 교전 — 대미지는 per-thread 버퍼에 누적 후 순차 병합(결정론) (병렬)
7. projectile: 발사·비행·착탄 광역 판정 (병렬)
8. siege     : 성벽/성문 HP, 등반 진행, 낙하물 (직렬, 소량)
9. morale    : 1/8 샘플 갱신 + 패주 전파 (병렬)
10. cleanup  : 사망 처리, 데칼 큐 적재, 통계, 승패 판정
```

대미지 적용을 병합 단계로 분리하는 이유: 쓰기 경합 제거 + **스레드 수와 무관한 결정론적 결과**(고정 청크 → 인덱스 순 병합).

### 2.5 발사체

```rust
pub struct ProjectilePool {   // 고정 20만, 프리리스트
    pos: Vec<[f32; 2]>, vel: Vec<[f32; 2]>,
    kind: Vec<u8>,            // 화살/볼트/투석/발리스타
    t_land: Vec<u16>,         // 착탄 틱 (발사 시 계산)
    target: Vec<[f32; 2]>,    // 낙하 지점 (산포 적용 완료값)
    z_arc: Vec<f32>,          // 렌더용 포물선 높이 계수
}
```

곡사는 발사 순간 **낙하 지점과 비행시간을 확정**(산포 = 시드 난수)하고, 비행 중에는 렌더 보간만 한다. 물리 적분 없음 → 착탄 판정은 `t_land == tick`인 것만 그리드 질의. 발리스타는 직선 스윕(레이 vs 그리드) 특수 처리.

## 3. 렌더링 계획

### 3.1 유닛 인스턴싱 파이프라인 (최대 리스크 → 최우선 검증)

- 인스턴스 버퍼: `[x, y, atlas_idx, team_flags]` = 유닛당 12B → 30만 = 3.6MB, 매 프레임 스트리밍 업로드.
- 버텍스 셰이더에서 쿼드 확장(4정점 인스턴싱), 아틀라스 UV 룩업, 팀 컬러 틴트, `prev_pos→pos` 보간(보간 계수 uniform).
- 드로우콜: **유닛 전체 1콜** + 발사체 1콜 + 데칼 1콜 + 지형 청크 n콜.
- 줌 LOD: 화면당 유닛 픽셀 < 2px이면 아틀라스 대신 단색 포인트 모드(같은 파이프라인, 플래그만 전환).
- 프러스텀 컬링: 그리드 셀 단위로 가시 범위 인스턴스만 수집.

### 3.2 데칼 (시체/핏자국)

- 월드 크기 오프스크린 RT(4096², 지형과 별개 레이어)에 사망 이벤트를 **한 번만** 스탬프 → 이후 렌더 비용 0. 큐에 쌓아 프레임당 최대 2천 개씩 소화(대량 사망 프레임 스파이크 방지).

### 3.3 스프라이트 에셋

- **전 구간 절차 생성 아틀라스** 확정(ASSETS.md v0.2): 코드가 도형으로 그려 굽는다. 외부 아트 파일 없음 → 단일 exe에 유리, 아트 의존성 제로.
- 병종별 실루엣 규칙은 ASSETS.md의 표를 따른다(방패 원, 관통 창대, 각진 강철 몸통, 활 호, T자 석궁, 말 타원 등).

## 5. 성능 예산표 (30만 유닛, 8코어 기준)

| siege + cleanup | 4 ms | |

렌더는 별도 스레드 아님(macroquad 단일 스레드 루프) — 시뮬 20Hz, 렌더 60fps 보간이므로 프레임당 시뮬 비용은 평균 1/3틱. 틱이 몰리는 프레임은 최대 1틱만 수행하고 나머지는 이월(스파이크 평탄화).

각 시스템은 `criterion` 마이크로벤치 + 인게임 프로파일 오버레이(F3)로 상시 계측한다.

## 6. 테스트 전략

1. **결정론 테스트**: 동일 (config, seed) 2회 → 매 100틱 상태 해시(FNV) 비교. 스레드 수 1/4/8 교차 검증. CI 필수.
2. **상성 회귀 시나리오**: M2부터 누적(§4의 2.7, 3.4, 4.7). 각 시나리오는 `기대 승자 + 허용 손실 범위`를 assert — 규칙 수정이 상성을 깨면 CI가 잡는다.
3. **성능 벤치**: 합성 30만 배치로 시스템별 시간 측정, 예산표 초과 시 CI 경고.
4. **헤드리스 퍼징**: 랜덤 설정 100판 완주(패닉/NaN/무한전투 감지, 최대 틱 상한).

## 부록 A. M1 실측 결과 (2026-08-27)

계획 대비 실제로 나온 수치와, 구현하며 계획을 고친 지점들.

### 성능 (4코어 개발 환경, 30만 유닛)

| 시스템 | 계획 예산 | 실측 | 비고 |
|---|---|---|---|
| movement | 15 ms | 14.4 ms | |
| grid | 3 ms | 3.5 ms | |
| combat | 10 ms | 2.7 ms | 탐색 반경 축소 효과 |
| flow | 5 ms | 0.6 ms | 라운드로빈이 충분히 저렴 |
| **합계** | **50 ms** | **21.2 ms** | 최악 43 ms |

메모리는 30만에 14.1 MB(계획 17.4 MB). 목표 사양이 8코어인 점을 감안하면 예산에 여유가 상당하다.

### 계획에서 바뀐 것

1. **그리드를 월드 전체가 아니라 살아있는 유닛의 경계 상자에만 친다.**
   3km² 에 2m 셀을 고정으로 깔면 236만 셀의 prefix sum 을 매 틱 도느라, 유닛이
   2천 명이든 30만 명이든 6.6ms 를 먹었다. 경계 상자로 좁히고 셀 수가 유닛 수의
   세 배를 넘으면 셀을 키우도록 하니 0.2ms 가 됐다.

2. **플로우 필드를 8방향 양자화에서 적분장 기울기 + 이중선형 보간으로 바꿨다.**
   양자화하면 셀 경계마다 진행 방향이 끊겨, 대형이 12m 간격의 세로 빗살로 갈라진다.

3. **대상 탐색 여유를 2.5m → 0.6m 로 좁혔다.** 아래 대칭성 항목 참고.

4. **겹침을 위치 수준에서 해소한다(POS_FIX).** 속도에만 반발력을 실으면 목표
   방향 추진력을 이기지 못해 두 대형이 서로를 통과해 버린다.

5. **헤드리스 모드(1.8)를 앞으로 당겼다.** 개발 환경에 GUI 가 없어 시뮬레이션
   검증을 콘솔과 스냅샷 이미지로 해야 했다. 결과적으로 계측이 훨씬 촘촘해졌다.

### 대칭성 — 가장 값비쌌던 버그

동일 병종·동일 병력의 양군인데 40시드 중 30번을 한쪽이 이겼다(z = -5.0).
배치를 뒤집으면 편향도 뒤집혀 팀 번호가 아니라 진영 위치를 따라간다는 것까지
좁힌 뒤, 요소를 하나씩 꺼가며 범인을 찾았다.

| 가설 | 결과 |
|---|---|
| 플로우 갱신 위상차 | 편향 유지 (z=-4.9) |
| 그리드 순회 방향 | 편향 유지 (z=-5.5) |
| 방패 정면 판정 | 편향 유지 (z=-3.8) |
| 겹침 위치 보정 | 편향 유지 (z=-3.5) |
| **대상 추격** | **편향 소멸 (z=+1.1)** |

원인은 대상 탐색 반경이었다. 대상을 잡은 유닛은 진형 대신 그 적에게 직진하는데,
여유가 2.5m 나 되어 접적 순간 먼저 적을 포착한 쪽이 대형을 풀고 끌려나갔다.
계측상 접적 직후 한쪽은 82명이 교전에 들어간 반면 다른 쪽은 7명이었다.
여유를 0.6m 로 좁히자 z = -0.97 로 사라졌다.

이 과정에서 함께 잡은 것 두 가지:
- 피해를 한 패스로 적용하면 "이미 죽은 대상에 대한 타격"이 팀 번호 순서대로
  버려져, 먼저 처리되는 진영만 공격을 낭비한다. 차감과 사망 판정을 분리했다.
- 대형의 모자란 마지막 행이 항상 북쪽에 놓여 남쪽 진영만 최전선에 구멍이 뚫린
  채 개전했다. 대형에 정면 방향을 부여해 빈 행을 후방으로 보냈다.

셋 다 회귀 테스트(`mirror_battle_stays_balanced`)로 고정했다. 개별 전투의 편차는
원래 크므로(전선이 한 번 무너지면 걷잡을 수 없다) 평균이 아니라 z 값으로 판정한다.

### 남은 과제

- **작업 1.4(실시간 렌더)는 미착수.** 개발 환경에 GUI 가 없어 검증이 불가능하다.
  대신 전장 스냅샷 도구(`src/bin/snapshot.rs`)로 시뮬레이션을 눈으로 확인했다.
  실시간 렌더러는 Windows 실기에서 확인해야 한다.
- 두 대형이 여전히 서로를 어느 정도 파고든다. 사기·패주(M2)가 들어오면 밀린 쪽이
  무너져 나가므로 양상이 크게 달라질 것이라, 그때 다시 본다.

### 개발용 도구

| 명령 | 용도 |
|---|---|
| `orc-war -n 300000 --bench` | 전투 실행 + 페이즈별 성능 |

## 부록 B. 목표 기준기 확정 (2026-08-27)

개발·검증의 기준으로 삼는 실제 PC.

| 항목 | 사양 |
|---|---|
| 기기 | OMEN by HP Gaming Laptop 16-xf0xxx |
| CPU | AMD Ryzen 7 7840HS (Zen4, 8코어 16스레드, 3.8GHz / 부스트 ~5.1GHz) |
| RAM | 16GB DDR5-5600 (15.3GB 사용 가능) |
| GPU | NVIDIA RTX 4060 Laptop 8GB + Radeon 780M 내장 (하이브리드) |
| 저장소 | 477GB 중 131GB 여유 |
| OS | Windows 11 Home 25H2 (x64) |

계획서가 잡았던 목표 사양(8코어 + GTX 1060급)을 넉넉히 상회한다.

### 성능 여유 추정

개발 환경은 Xeon 2.1GHz 4코어라 기준기보다 코어 수도 코어당 성능도 낮다.
스레드를 늘려가며 잰 확장 효율은 약 80%로 거의 선형이었다.

| 스레드 | 30만 유닛 |
|---|---|
| 1 | 74.0 ms |
| 2 | 39.7 ms |
| 4 | 23.0 ms |

기준기는 코어가 두 배(8물리/16논리)이고 클럭도 1.8~2.4배, Zen4 IPC 이득까지
감안하면 **30만 유닛에서 5~10 ms/tick** 대가 나올 것으로 본다. 예산 50ms 대비
5~10배 여유이므로 **4배속 관전에도 문제가 없다.**

개발 환경 4코어에서 이미 50만 유닛이 36.6 ms/tick(메모리 23.5MB)로 돌아간다.
30만은 상한이 아니라 편안한 목표치다.

실측은 기준기에서 `dist/성능측정.bat` 으로 확인한다.

### 이 기기 때문에 설계에 반영할 것

1. **하이브리드 GPU** — RTX 4060 과 Radeon 780M 이 함께 있다. 렌더러가 아무 어댑터나
   잡으면 내장 GPU 로 떨어져 성능이 크게 깎인다. 어댑터 요청 시 고성능 선호를
   명시하고, Windows 에서는 `NvOptimusEnablement` / `AmdPowerXpressRequestHighPerformance`
   심볼을 내보내 드라이버가 외장 GPU 를 고르게 한다. (렌더러 착수 시 최우선 항목)

2. **노트북 전력·발열** — 배터리 모드에서는 지속 성능이 절반 아래로 떨어진다.
   틱 예산을 넘기면 프레임을 버리는 대신 시뮬 배속을 자동으로 낮추는 우아한 저하가
   데스크톱보다 더 중요하다(작업 6.2). 렌더는 vsync 를 기본으로 켜서 불필요한
   발열을 만들지 않는다.

3. **RAM 16GB** — 유닛 데이터는 30만에 14MB 라 여유롭다. 다만 다른 프로그램과
   공유하는 환경이므로 전체 상주 메모리를 1GB 아래로 유지한다. 시체 데칼용
   오프스크린 버퍼(4096² RGBA = 64MB)가 가장 큰 단일 할당이 될 것이다.

4. **빌드 대상** — 배포는 `x86_64-pc-windows-msvc` 를 기본으로 한다(GNU 대비 성능·
   호환성 우위). 리눅스 개발 환경에서 즉시 확인할 때는 `x86_64-pc-windows-gnu`
   크로스 컴파일을 쓴다. 둘 다 CI 에서 굽는다.

## 부록 C. M2 구현 노트 (2026-08-27)

사기·기병 충격·창벽·원거리를 넣었다. 병종 교리 AI(작업 2.6)만 남았다.

### 사기 — 격자로 푼다

유닛마다 주변을 훑어 사기를 계산하면 30만에서 감당이 안 된다. 전장에 16m 격자를
깔고 "이 구역에서 최근 무슨 일이 있었나"(사망·패주)를 누적한 뒤, 유닛은 자기 발밑
칸만 읽는다. 충격은 매 틱 조금씩 이웃 칸으로 번지고 가라앉는다. 국소 붕괴가
옆으로 전염되는 현상이 이 위에서 저절로 나온다. 30만에서 2.4ms.

계수를 잡으며 배운 것:

- **교전 중에도 버티는 항(HOLD)이 없으면 안 된다.** 붙어 싸우는 유닛의 사기가
  내려가기만 하면, 어느 쪽도 이기지 못한 채 22% 손실에 전군이 함께 무너진다.
- **재집결을 쉽게 두면 전투가 끝나지 않는다.** 패주 → 이탈 → 회복 → 복귀 →
  재패주가 무한히 반복된다. 복귀 문턱을 높이고(기준치의 75%), 패주 중 회복을
  35%로 낮추고, 500틱 넘게 달아난 병력은 `Fled` 로 전장에서 빼 버린다.

### 돌격 — 한 명이 아니라 대열을 친다

처음에는 표적 하나만 때리게 했더니 중장기병이 동수의 방패 보병에게 졌다
(교환비 1:0.52). 돌격의 값어치는 한 명을 베는 게 아니라 대열을 뚫고 지나가는 데
있다. 접촉 지점 반경 2.2m를 통째로 휩쓸게 하고(최대 6명), 말 위에서 내려찍는
타격은 방패를 절반만 인정하도록 고쳤다.

창벽은 그 반대다. 자리를 지킨(속도 0.35m/s 미만) 장창병이 정면 120도로 받으면
충격이 통째로 무효화되고, 기병이 자기 운동량의 두 배를 되받는다.

### 원거리 — 사격 시간을 정하는 것은 사거리가 아니라 화살통

두 번 크게 틀렸다.

1. **발사에 쿨다운을 안 걸었다.** 궁수가 초당 다섯 발(설계는 0.9발)을 쏘아
   검방 보병 600명을 손실 0으로 전멸시켰다.
2. **화살이 무한이었다.** 쿨다운을 고쳐도 궁수는 접근 시간 내내 쏘았다. 120m를
   좁히는 75초 동안 600명이 4만 발을 날린다. 병종마다 탄약(궁수 24, 석궁 20)을
   주자 비로소 "쏘다가 붙는" 전투가 됐다.

궤적은 적분하지 않는다. 쏘는 순간 낙하 지점과 비행 시간을 확정하고 착탄하는 틱에만
판정한다. 정확도는 산포로 표현하므로, 빗나간 화살도 그 자리에 누가 있으면 맞는다 —
밀집 대형에 화살비가 재앙이 되는 이유가 규칙으로 들어간다.

### 상성 실측 (동수 600 대 600)

| 대결 | 결과 |
|---|---|
| 중기병 vs 궁수 | 중기병 압승 (교환비 1:20) |
| 중기병 vs 장창병 | 창벽 승 — 정면 돌격이 갈린다 |
| 중기병 vs 검방 보병 | 호각 |

중장기병이 밀집 중보병과 호각인 것은 의도한 결과다. 중장기병의 값어치는 정면
돌파가 아니라 사수·측면·패주병을 치는 데 있고, 궁수 상대 1:20 이 그것을 보여준다.

여섯 대결 모두 회귀 테스트(`tests/matchups.rs`)로 못 박았다.

### 남은 과제

- **병종 교리 AI(2.6)** — 지금은 모든 병종이 똑같이 정면으로 걸어들어간다.
  경기병이 방패벽에 박아 전멸하고, 궁기병이 카이팅 대신 근접전을 한다.

## 부록 D. 교리 AI와 M3 지형 (2026-08-27)

### 교리 — 병종마다 다른 장을 읽힌다

모든 병종이 같은 플로우 필드를 보면 경기병이 방패벽에 정면으로 박아 전멸한다.
팀별로 장을 하나씩 더 굽고(무른 표적 = 적 사수와 무너진 부대) 기병이 그것을 읽게 했다.

핵심은 **기병용 장에 적 전열의 통행 비용을 얹은 것**이다. 이게 없으면 기병이
뒤에 선 사수를 노리랍시고 방패벽 한복판으로 걸어들어간다. 얹어 주면 비로소
옆으로 돈다. 8만 혼성 전투에서 기병이 양익 끝에서 교전하는 것을 확인했다.

사수는 "방금 쏘았다"(= 사거리 안에 표적이 있다)면 자리를 지킨다.

### 돌격 충격은 한 번도 발생한 적이 없었다

M2 내내 그랬다. 전투 단계가 매 틱 상태를 `Fight`/`Advance` 로 덮어써서, 돌격
가속 카운터가 0에서 벗어나질 못했다. 충격 대미지에 곱해지는 가속 계수가 항상
0이었으므로 충격은 늘 0이었다. 상성 실측이 그럴듯해 보였던 것은 순전히 일반
근접전 결과였다.

전투 단계가 `Charge` 상태를 건드리지 않게 고치자 상성이 크게 바뀌었다.

| 경기병 vs 검방 보병 | 보병 압승 | 경기병 우세 → 계수 조정 후 대등 |

이때 경기병까지 전열을 뚫어버려서, 충격에 실리는 비율을 병종 속성(`charge_power`)
으로 분리했다. 랜스를 겨누고 마갑을 두른 중장기병만 1.0 이고 경기병은 0.30 이다.
말을 탔다고 다 같은 돌격이 아니다.

## 부록 E. M4 공성전 (2026-08-27)

### 성벽을 지형에 찍는다

가장 큰 설계 판단은 성벽과 해자를 **지형에 직접 찍어 넣은 것**이다. 통행 규칙을
따로 만들 필요 없이 기존 경로탐색이 "여기는 못 지나간다"를 알아듣고, 성벽이
무너지면 그 칸의 지형만 잔해로 바꾸면 길이 열린다.

성벽은 40m 짜리 구간으로 쪼개 각각 내구도를 갖는다. 투석기가 구간을 무너뜨리면
잔해 경사로가 되고, 파성추가 성문을 부수면 그 자리가 뚫린다.

### 해자가 성을 완전히 봉했다

처음에는 성벽을 아무리 부숴도 아무도 들어가지 못했다. 해자가 성을 빙 두르고
있어 성문 앞 다리가 유일한 입구였고, 6천 명이 그 통로에서 정체했다. 투석기로
성벽을 부수는 일에 아무 의미가 없었다.

무너진 성벽의 돌더미가 **그 앞의 해자도 메우도록** 고쳤다. 이제 성벽을 부수면
통로가 함께 열린다.

### 성벽이 화살을 막지 않았다

공격군이 8천 명 중 970명만 잃고 이겼다. 성 밖에 선 채로 수비군을 활로만 지워
버린 것이다. 성벽의 값어치는 사람을 막는 것만이 아니라 시선을 막는 데도 있으므로,
흉벽 너머로 넘긴 화살은 위력의 30%만 남기도록 했다.

### 낙하물을 두 번 틀렸다

처음에는 성벽에 붙어 지키는 판정을 6m 로 잡아 **한 번도 발동하지 않았다**.
수비 대열은 성벽 안쪽으로 십수 미터 물러나 서기 때문이다. 지형을 더듬는 대신
성벽 안쪽 면까지의 거리를 재도록 바꿨다(성은 사각형이라 계산이 싸다).

그러자 이번에는 반대로 수비 천 명이 매번 반경 안을 통째로 쓸어버려, 공격군이
성문 근처에 발도 못 붙였다(43,366회 타격, 공성 실패). 돌 하나는 한둘을 맞힌다.
사람당 표적 수를 제한하고 위력을 낮춰 균형을 잡았다.

### 사격이 전체의 77% 를 먹고 있었다

공성전이 같은 규모 야전보다 일곱 배 느렸다. 재 보니 사격 한 단계가 18.3ms,
전체 23.8ms 중 77% 였다.

원인은 사수가 사거리 120m 안에서 표적을 찾겠다고 격자를 훑는 데 있었다.
야전에서는 병력이 넓게 퍼져 격자 칸이 커지므로 티가 나지 않지만, 공성전은 성
주위에 밀집해 칸이 2m 로 잘게 쪼개진다. 반경 120m 면 칸 만 사천 개다.

화살은 애초에 사람을 조준하는 무기가 아니다. 개별 적을 찾는 대신, 진격 방향으로
몇 군데를 찔러 보고 사람이 있는 칸을 골라 그쪽으로 쏘도록 바꿨다(사기 격자의
밀도를 재활용). **18.3ms → 0.88ms, 22배.**

### 실측 (8천 대 3천, 해자 있음)

| 수비 | 결과 | 공격측 손실 | 수비측 전사 |
|---|---|---|---|
| 3,000 | 함락 (155초) | 2,924 | 2,445 |
| 4,500 | 함락 (229초) | 7,975 | 3,568 |

수비가 1.5배로 늘자 공격측 손실이 2.7배가 됐다. 성을 뜯어내는 값이 병력비에
가파르게 반응한다.

성능은 8천 유닛 공성 기준 6.3 ms/tick (이동 1.4 · 사기 2.6 · 공성 0.4 · 사격 0.3).

### 남은 과제

- **성벽 등반이 한 번도 일어나지 않는다.** 성문과 붕괴구가 있으면 경로탐색이
  그쪽을 고르기 때문인데, 이는 올바른 판단이다. 다만 공성병기 없이 사다리만
  주는 시나리오를 만들어 등반 경로 자체를 검증해야 한다.
- ~~야전 30만이 30.3 → 41 ms/tick 으로 느려졌다~~ → **회귀가 아니었다. 부록 F 참고.**
- 성벽 위 병력을 별도 층으로 두지 않고 "성벽 안쪽에 붙어 선 병력"으로 근사했다.
  탑뷰 2D 에서 높이를 어떻게 보여줄지는 렌더러를 붙일 때 함께 정해야 한다.

## 부록 F. 야전 성능 — 회귀는 없었다 (2026-08-27)

### 있지도 않은 회귀를 쫓았다

M4 를 마치며 "야전 30만이 30.3 → 41 ms/tick 으로 느려졌다"고 적었다. 확인해 보니
사실이 아니었다. M3 시점 커밋(e5eb386)을 따로 받아 빌드해 같은 조건으로 나란히
재니 이렇게 나온다.

| | movement | 합계 |
|---|---|---|
| M3 (e5eb386) | 17.2 ms | 28.0 ms |
| M4 (현재) | 17.1 ms | 27.9 ms |

**41ms 라는 숫자는 그때 백그라운드에서 `cargo test` 가 돌고 있어서 나온 것이다.**
4코어에서 테스트와 벤치가 CPU 를 나눠 쓴 결과였다. 최악값 70~89ms 도 같은 이유다.
부하 없이 재면 최악은 42ms 이고, 그마저 t=28 — 스폰 직후 대형이 가장 빽빽할 때다.

교훈은 단순하다. **벤치는 놀고 있는 기계에서 재야 한다.** 반복 측정 기능
(`--repeat N`)을 넣었지만 이걸로 부하를 잡을 수는 없다. 함께 도는 작업이 있으면
세 회차가 나란히 느려져 편차로는 드러나지 않기 때문이다. 그래서 출력에 그 사실을
한 줄 적어 둔다.

### 대신 실제로 손볼 것을 찾았다

이동 단계가 전체의 60% 였다.

**1. 경사를 미리 구워 둔다.** 유닛마다 진행 방향의 경사를 구하려고 고도를 두 번
보간했는데, 이중선형 보간 한 번이 배열을 네 번 뒤지므로 유닛당 여덟 번이었다.
30만이 매 틱 그 짓을 한다. 지형이 바뀔 때 칸마다 기울기를 한 번 구워 두고
조회 한 번으로 끝내도록 바꿨다. **17.4 → 14.5 ms**

**2. 격자에 위치를 함께 담는다.** 격자는 유닛 번호만 들고 있었고, 이웃을 훑을
때마다 `pos[j]` 를 찾아 읽느라 무작위 접근이 일어났다. 순회에 필요한 값(위치·
병종·팀)을 셀 순서대로 함께 담아 순차 접근으로 바꿨다. **14.5 → 13.4 ms**

항목을 20바이트로 만들었을 때는 격자 재구축이 그만큼 무거워져 순이득이 없었다
(movement −1.1ms, grid +1.0ms). 반경 대신 병종 번호를 담아 16바이트로 줄이자
비로소 이득이 남았다.

| | movement | grid | 합계 |
|---|---|---|---|
| 시작 | 17.4 | 4.1 | 28.3 |
| 경사 격자 | 14.5 | 4.1 | 25.0 |
| + 격자 패킹 | 13.4 | 4.9 | **24.5** |

30만 유닛 기준 **28.3 → 24.5 ms/tick (13% 개선)**, 이동 단계만 보면 23% 다.
결정론과 상성 회귀 테스트는 그대로 통과한다.

## 부록 G. 실시간 관전 화면 (2026-08-28)

### GPU 를 쓰지 않기로 했다

계획서는 miniquad 인스턴싱을 잡았지만 `minifb` 로 갔다. 창·화소 버퍼·입력을
한 크레이트가 해결하고, Windows 에서 win32 를 직접 쓴다.

결정적인 이유는 기준기가 하이브리드 노트북이라는 점이다. RTX 4060 과 Radeon 780M
이 함께 있어 어댑터를 잘못 잡으면 내장으로 떨어지는데, 그 문제를 애초에 만들지
않는 편이 낫다. 이 개발 환경에서는 창을 띄워 확인할 수가 없어, 처음 실행이
곧 실전이다. 손댈 곳이 적을수록 좋다.

성능도 CPU 로 충분했다. 그림이 점과 사각형뿐이라 셰이더로 얻을 것이 별로 없다.

| 장면 | 렌더 시간 |
|---|---|
| 야전 6만 (전체 보기) | 4.9 ms |
| 야전 6만 (400m 확대) | 5.0 ms |
| 야전 30만 | 8.4 ms |
| 공성전 4만 | 8.1 ms |

1440×810 기준이고 60fps 예산은 16.7ms 다. 대부분이 지형이며(픽셀마다 지형과
고도를 조회한다) 병력은 30만에서도 3.7ms 다.

### 창 없이 화면을 검증한다

GUI 가 없는 환경에서 렌더러를 만드는 것이 이번 작업의 실질적인 어려움이었다.
해법은 단순하다. **실제 렌더 경로를 그대로 태워 한 장을 파일로 굽는 도구
(`preview`)를 함께 만들었다.** 창에 나올 그림과 같은 코드가 그린 것이라,
HUD 글꼴부터 색 배치까지 창 없이 확인할 수 있다.

이걸로 두 가지를 잡았다.

- **공성전에서 성이 화면 위로 잘렸다.** 카메라를 병력 위치만 보고 맞춰서다.
  성곽 범위도 함께 담도록 고쳤다.
- **확대하면 핏자국이 격자 사각형으로 보였다.** 시체가 격자에 맞춰 쓰러질 리는
  없으므로 이웃 칸까지 섞어 읽어 경계를 뭉갰다.

### 구성

- `render::Camera` — 화면과 월드 사이 변환. 화소당 미터(mpp)로 확대율을 표현한다
- `render::Decals` — 시체는 화면이 아니라 월드 격자(4m)에 누적한다. 카메라가
  움직이기 때문이다
- `render::font` — 5x7 비트맵 글꼴. 글꼴 크레이트를 끌어오는 대신 필요한 글자만
  손으로 찍었다. 한글은 이 방식으로 감당할 수 없어 창 제목에 싣는다
- `watch` — 창, 입력, 시뮬 루프
- `preview` — 같은 렌더 경로로 한 장을 파일로

### 조작

스페이스 일시정지 · `[` `]` 배속(0.5~16x) · WASD/화살표/드래그 이동 ·
휠 또는 QE 확대축소 · F 전체 보기 · R 재시작 · Esc 종료

배속을 기계가 감당하는 속도 위로 올리면 따라잡기를 포기하고 프레임을 지킨다
(`MAX_STEPS_PER_FRAME`). 화면이 멈추는 것보다 배속이 덜 나오는 편이 낫다.

### 남은 것

- 지형은 카메라가 그대로면 다시 그릴 필요가 없다. 아직 매 프레임 다시 그린다
- 성벽 위 병력을 따로 층으로 보여주지 않는다. 지금은 성벽 안쪽에 붙어 선 것으로
  그려진다

### 지형 캐시 (2026-08-28)

지형 그리기가 프레임의 대부분을 먹고 있었다(30만 기준 렌더 12.4ms 중 9.2ms).
카메라가 멈춰 있으면 매 프레임 같은 그림을 다시 만드는 셈이다.

배경을 담아 두고 재사용한다. 문제는 시체가 매 틱 쌓인다는 점인데, 그것 때문에
배경을 통째로 버릴 이유는 없다. 값이 바뀐 칸만 기록해 두었다가 그 언저리만
덧칠한다(이웃 칸까지 섞어 읽으므로 둘레 두 칸까지).

| 장면 | 통째로 | 캐시 | |
|---|---|---|---|
| 야전 6만 (프레임당 사망 55) | 7.40 ms | 1.08 ms | 6.9배 |
| 야전 30만 (사망 179) | 7.83 ms | 1.11 ms | 7.0배 |

있는 수준이 됐다.

#### 회귀 테스트가 잡은 것

"덧칠한 배경이 통째로 그린 것과 화소 단위로 같아야 한다"는 테스트를 먼저 썼고,
두 가지가 걸렸다.

1. **화소 좌표가 반 칸 어긋나 있었다.** 전체 그리기는 화소 좌상단을, 덧칠은
   화소 중심을 썼다. 465화소가 달랐다.
2. **부동소수 누적.** 전체 그리기가 `wx += mpp` 로 좌표를 더해 나가는 동안
   오차가 쌓여, 직접 계산하는 덧칠 경로와 미세하게 어긋났다. 색 반올림 경계에
   걸린 40화소가 한 단계 다른 색이 됐다. 두 경로 모두 `x0 + col * mpp` 로 통일했다.

둘 다 눈으로는 알아채기 어렵고(전장 어딘가에 희미한 네모 자국이 남는 정도),
시간이 지나며 쌓이면 그제야 보였을 종류의 것이다.
